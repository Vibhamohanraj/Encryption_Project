# SecureFile Binary Container Specification (Version 1)

This document defines the binary layout, field encoding, endianness rules, and authentication model for encrypted files produced by **SecureFile**.

---

## 1. Overall File Layout

A SecureFile archive consists of three contiguous sections:

```text
+-------------------------------------------------------------+
| Header (Fixed 60 bytes, authenticated via AAD)             |
+-------------------------------------------------------------+
| Ciphertext (Variable length N bytes, AES-256-GCM)            |
+-------------------------------------------------------------+
| Authentication Tag (Fixed 16 bytes, AES-256-GCM GMAC)       |
+-------------------------------------------------------------+
```

Total file size is exactly:
$$\text{Total Size} = 60 + N + 16 = N + 76 \text{ bytes}$$

For an empty file ($N = 0$), the file size is exactly $76$ bytes. Any file smaller than 76 bytes is considered truncated and immediately rejected.

---

## 2. Header Structure (60 Bytes)

All multi-byte integer fields are stored in **Little-Endian** byte order.

| Offset | Field Name | Type | Size | Description |
| :---: | :--- | :---: | :---: | :--- |
| `0x00` | `magic` | `uint8_t[8]` | 8 bytes | Fixed magic ASCII identifier: `"SECFIL01"` (`0x53, 0x45, 0x43, 0x46, 0x49, 0x4C, 0x30, 0x31`) |
| `0x08` | `version` | `uint32_t` | 4 bytes | Format version integer (Currently `1`, Little-Endian) |
| `0x0C` | `kdf_algorithm` | `uint32_t` | 4 bytes | KDF identifier (`2` represents `crypto_pwhash_ALG_ARGON2ID13`) |
| `0x10` | `opslimit` | `uint64_t` | 8 bytes | Argon2id iteration/time cost parameter (Little-Endian, default: 3) |
| `0x18` | `memlimit` | `uint64_t` | 8 bytes | Argon2id memory cost in bytes (Little-Endian, default: 64 MiB) |
| `0x20` | `salt` | `uint8_t[16]` | 16 bytes | Cryptographically secure random salt for Argon2id key derivation |
| `0x30` | `nonce` | `uint8_t[12]` | 12 bytes | Cryptographically secure random 96-bit initialization vector (IV) for AES-GCM |

---

## 3. Cryptographic Binding (AAD)

During both encryption and decryption:
1. The full **60-byte serialized header** is supplied to the AES-256-GCM cipher as **Additional Authenticated Data (AAD)**.
2. Because the header is bound into the authentication tag calculation, any modification to metadata (e.g. altering the version, tampering with KDF parameters, or flipping bits in the salt or nonce) will cause authentication tag verification to fail during decryption.

---

## 4. Ciphertext & Streaming

- The plaintext is encrypted using **AES-256-GCM** in 64 KiB bounded chunks.
- AES-GCM behaves as a stream cipher for confidentiality; plaintext of length $N$ produces ciphertext of length $N$.
- Arbitrarily large files are processed without loading the full file into memory.

---

## 5. Authentication Tag (16 Bytes)

- The final 16 bytes of the container represent the GCM authentication tag generated by OpenSSL `EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_GCM_GET_TAG, ...)`.
- During decryption, the tag is set using `EVP_CTRL_GCM_SET_TAG` and verified by `EVP_DecryptFinal_ex()`.
- If verification fails, decrypted data is deleted immediately and never published to the target destination.
